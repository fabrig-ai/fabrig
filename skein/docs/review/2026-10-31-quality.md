# skein: code-quality review

2026-10-31. Source: github `origin/main` at `3371027`, a fresh clone. The primary checkout `~/src/fabrig/main` is at `5608b28` and was not touched. Scope: `skein/`, about 481k lines of Rust.

Method:
- **A holistic pass by me.** It covered the foundation docs, the crate graph and API probes, and produced a shared rubric: [`2026-10-31-quality/rubric.md`](2026-10-31-quality/rubric.md).
- **12 area reviewers and one cross-area reviewer.** Each read its area's production code and tests together. They read hot spots closely and sampled the rest. This is an assessment, not a line-by-line audit.
- **Spot checks by me.** I checked about 20 headline claims against the source; the results are in the last section.
- **Full reports:** the reviewers' full reports are in [`2026-10-31-quality/`](2026-10-31-quality/), `01..13-*.md`.

## Verdict

**skein is careful code with structural debt.** Line by line it is good: the subset is held, expectations name their invariants, arithmetic is checked, and test names read as sentences about behaviour. The weak spots are:

- **Economy (2/5 in 11 of 12 areas).** The same mechanism is hand-written again and again: in each component, each dialect, each fake face, and each test harness.
- **Primitives and Organization (mostly 2–3).** Shared pieces that should exist do not. Layout rules are written once and applied in three or four ways.
- **Uneven house style.** About half the state machines follow programming-model 5.4 (state in the enum, `mem::replace`, one follow-state function). The newer and larger components keep state in structs of flags and Options instead.

**Size.** The reviewers' savings estimates add up to roughly 20–30k lines, about 5% of the tree. The estimates overlap and are unverified, so treat them as an order of magnitude. Most of that is in tests and in the forge family. The tree is not bloated in general. The waste is concentrated in a few repeated shapes, and fixing those shapes also removes drift that has already happened between copies.

**The house rules are rarely the real cost.** Where a reviewer blamed a rule (wide or-patterns, exhaustive variant lists), the real cause was usually the shape of a type: a flat 34-variant `Answer`, a `Reply` that mixes both dialects, read plans built as one bag. Reshaping the type recovers most of it within the rules.

## Themes, ranked by payoff

### 1. Missing shared primitives at the component and harness layer

This is the single largest theme. Each item below is written privately in 2 to 50 places.

**1a. The socket + optional TLS (+ HTTP) transport is written four times.**
- **Where:**
  - `skein-forge-connection/src/connection.rs`
  - `skein-forge-setup/src/host/connection.rs`
  - `skein-oauth-accounts/src/exchange.rs` (`Web`)
  - `skein-llm-connection/src/call.rs`
- **What each copy has:** a socket token, an `Option<tls::Client>`, the cipher and plain queues, the handshake, routing, upload, and close/abort.
- **Drift already present (verified):**
  - Only oauth-accounts and llm-connection send TLS `close_notify` (`exchange.rs:494`, `call.rs:326`). Neither forge component does.
  - Neither forge component has an `Abort` request, though 5.2 requires one.
  - The four copies use three queue-naming schemes and four encodings of close/abort.
  - llm-connection and oauth-accounts each define the same `enum Lifecycle { Live, Closing, Aborting, Closed }`.
- **Also near-copied:** `Transport` and `host()` (identical up to doc wording and path qualification).
- **Fix:**
  - One concrete transport struct (`Link`) over io and tls, with `connected`, `up`, `down`, `close(abort)`, `pump` and `has_work`.
  - A shared `Endpoint`.
  - A forge exchange composition in skein-forge (as skein-llm composes for LLM), used by both forge-connection and forge-setup.
- **Size:** about −900 to −1,300.

**1b. The io stage (resume → up → fire → down) is hand-written in every host.**
- 39 `io::resume` call sites sit outside skein-io.
- Only some of them check `MAX_OUT` before taking work, which testing-strategy 6 requires.
- The same ordering test exists twice, each `#[path]`-including another crate's private source (`tests/echo/.../scenarios.rs:249`, `tests/fake-peers/.../stages.rs:4`).
- **Fix:** `skein_io::stage::{up, down}` as free functions, tested once in tests/io. `examples/echo/service/src/io_stage.rs` is the model.
- **Size:** likely over 1,000 lines tree-wide.

**1c. The loop and referee surfaces cost boilerplate in every test world.**
- `Referee::act`, `next_deadline` and `overdue` have no defaults (`testing/skein-world/src/referee.rs:49-60`), while `starved` and `last_word` do. About 20 referees return `None` or do nothing for each.
- About 10 `enum Process` dispatchers forward the whole `Host` surface method by method (44–70 lines each), and the copies have drifted: `exit` and `state_digest` are forwarded in some and not others.
- `next_deadline` is a hand merge of a mechanism deadline and `next_policy_deadline` in every host.
- **Fix:**
  - Give those referee methods defaults.
  - Add `impl<H: Host + ?Sized> Host for Box<H>`, or a `Delegate` trait, in skein-shell.
  - Split `Host` into a mechanism deadline plus a policy deadline, and make `next_deadline` a provided method.
  - Make fake-peers' `Face` (the io pass) public in skein-world.
- **Size:** about −900 to −1,200 test lines.

**1d. Small gaps in lib, each filled privately 3–9 times.**
- `earliest(Option<Time>, Time)` ×4 (verified), plus inline copies in forge-connection.
- `Queue::clear` and `Stack::clear`: `for _ in 0..len { pop }` loops.
- An LRU ×4 in skein-forge's tables. The copies have drifted on overflow and on capacity 0.
- `hex` ×4+, decimal parse ×3+ (HTTP's client and server `decimal` are identical, verified), and percent/form codecs ×4 (fake-oauth's uses `loop`/`while` in a no_std step crate).
- `Header::new` ×9 plus about 35 inline literals.
- `Measure`/`put` ×3.
- Read-demand semantics (`Read::fits`, `takes`, `answered_by`) recomputed in 6+ places.
- The growth rule ×5 in lib itself, each with its own `GROWTH_FLOOR`.
- A `Lifecycle` enum.
- Slab iteration. Without it, oauth-accounts hand-rolls a linked list over the slab with nine `while let` walks.
- **Fix:** add these to lib, http and io. Each is mechanical and has high fan-out.
- **Size:** about −600 to −800.

**1e. The JSON read side stops too early.**
- `skein-oauth/src/json.rs` (397 lines) and `skein-llm/src/openai/json.rs` (532 lines) each rebuild the same value layer (`field`, `required`, `span`, `unsigned`, `text_ref`) and the same slice-driver loop as `tokenizer::validate`.
- skein-forge has two more field walkers (Forgejo's 559 lines, GitHub's 1,250), plus a third and a fourth in its fake server side.
- **Codec is not the answer.** It is a binary format by design (codec.md §3). "JSON from schemas" is listed as future work in codec.md §13 and json.md §8, so the hand decoders are correct today.
- **Fix:**
  - `skein_json::parse(input, &Limits) -> Document`, plus navigation on `Document`.
  - One table-driven walker in skein-forge, with the per-node rules in the tables.
  - Longer term, codegen for JSON.
- **Size:** about −1,000 to −1,600.

### 2. State machines that don't follow programming-model 5.4

The rule is good, but it is applied unevenly. Every reviewer found the same failure mode: a data-less (or partly data-carrying) `State`/`Phase` enum beside a struct of flags and Options that mean something in some states only. `expect("… before …")` calls then guard invariants the type could hold, and the phase and deadline are set at many sites instead of in one follow-state function.

| Where | Evidence |
|---|---|
| `skein-kv/src/store.rs` | Five module-wide lint opt-outs (verified: `disallowed_types`/`methods`, `struct_excessive_bools`, `too_many_lines`, `too_many_arguments`). 10 `loop`/`while`. Tuple scrutinee with a catch-all. Snapshot progress spread over 5 places. This is the durable store's recovery logic. **Highest priority.** |
| `skein-forge` read plans (`github/plans/reads.rs`) | Private copy of `api::Read`, a 26-variant flat `Stage`, 25 fields, 81 `self.stage =` assignments and no `mem::replace`. About 67 `if let`/`let…else` on own enums. |
| `skein-forge-connection` `Connection` | 31 fields. Phase assigned at 12 sites and deadline at 15. The design says the deadline is a function of the phase, set in one place. |
| `installations::GitHub` | 23 public fields. |
| `Hooked` | Three bools, four Options and a `forge: 0` sentinel. |
| `skein-oauth-accounts` | `State::Record` has 6 flags, one of them derivable. `Exchange` has 19 fields and stores a whole `oauth::Event`. |
| `skein-llm` `Client`, `skein-llm-connection` `Call`, fake-llm `provider` | Data-less `State`, 16 `state == State::X` checks. |
| io `file_layer` | 29 flat `Pending` variants listed out about 8 times, tuple matches with `_`, and the `Failed { …, committed: false, residue: None }` literal 53 times (verified; the reviewer said 32). |
| io `pipe.rs` | 22 fields and 6 bools. The demand face is copied three times. |
| `skein-channel` `Machine` | 11 bools. "Go closed" is written about 5 times. |
| `skein-http` SSE reader, `skein-json` collector, TLS native face | Diverge from the shape their sibling machines share. |
| forge-setup's Forgejo plans and host | `closing: Option<bool>`. Halting works by feeding a plan an unexpected event. |
| fake-forge servers (both faces) | Data-less `State` beside 8 Options. |
| `skein-browser`, `BrowserFace` | Hand-rolled `Vec<Option<T>>` slabs, boolean lifecycles, 25 Options. |

These conversions are mostly size-neutral. The payoff is that impossible states go away. Each should be its own task, starting with kv.

### 3. Copy-and-adapt between dialects and between fake faces

- **skein-forge:**
  - GitHub uses Forgejo as its common library: 44 imports of `forgejo::{id::unsigned, time, path, document::Body, decode::Malformed}`.
  - The rest is copied: plan `Failure`, the body/revision structs, hex.
  - The two dialects use opposite module shapes for the same jobs.
  - GitHub repeats the measure-then-write pass at 19 sites, where Forgejo has one `encode`.
- **forge-connection** wraps six parallel `Forgejo|GitHub` enums (`Exchange`, `Heard`, `Refusal`, `Request`, `Decoder`, `Body`), plus raw-request decisions of 85 and 52 arms that belong in skein-forge.
- **forge-setup** has a `Reply` that mixes both dialects, so 34 "reject the rest" arms list the other dialect's variants. Its `Plan` doesn't encode the dialect, so a mismatch is checked twice.
- **fake forge:**
  - Two near-identical connection machines that route replies two different ways.
  - A flat 34-variant `Answer`, so consumers either list 33 dead arms (Forgejo face) or use about 50 `let … else` (GitHub face, against 10.2).
  - The 70-variant `Request` is dispatched about 10 times (668 lines of `| Request::X { .. }`).
- **skein-llm:**
  - Two OpenAI request encoders kept in lockstep. One exists for the fake and as a test oracle.
  - `Output` ×3 and `Stop`/`Usage`/`Failure` ×2.
  - Request admission per dialect, with the error remapping written by hand 32 times.
- **Fix:**
  - Neutral crate-level modules in skein-forge.
  - Dialect-neutral plan types.
  - `Answer` nested by `Op`.
  - `Reply` split per dialect.
  - OpenAI decoding into `Prompt`, as Anthropic does.
- **Size:** about −3,000 to −4,000 production lines across the forge family and llm.

## Rule costs: decisions, not refactors

- **Test crates deny `wildcard_enum_match_arm`.** This is self-imposed; testing-strategy says tests are ordinary Rust. It forces 28-variant `Story` lists, about 21 full `Event` enumerations just to pick one variant out (forge-connection), and about 250 lines in oauth alone. **Recommend relaxing it in test crates,** or providing collector helpers.
- **No `From` with `?`.** This produces 32 hand-written remaps in llm and 12 forwarding accessors in codec. It is fixable within the rule by writing the inner helpers in the outer error type.
- **No closures.** This produces the measure-then-write pass at every JSON encoding site (about 76 sites, about 700 lines) and `manual_map` blocks. A lib helper over an enum-coded encoder could recover some of it.
- **Exhaustive matches over large enums** (49 roles, `kernel::Error`'s 26 variants spelled out about 13 times). Named category predicates, defined once beside each enum, keep the build-break property at about a third of the size.
- **Conformance scenarios return 9–12 observations each,** against "one behaviour per test". Worth an explicit exception in §10.

## Decisions

These are the calls on the questions the review raised. Each one says what changes in the docs and what changes in the code.

### D1. Fakes: shared wire codec, independent referee

**Call.** Keep what fake-forge.md already chooses: a fake's wire face uses the server side of the dialect crate (`fake-forge.md:355`, `:768`; `forge.md:518`). Do not give the fakes their own decoders.

**Why.**
- Independent codecs would roughly double the largest code in the tree: the forge wire layer alone is about 17k lines for about 125 routes.
- A second codec written by the same team from the same docs would mostly reproduce the same misreadings.
- What testing-strategy 4.1 actually asks for is an independent referee. Real bytes are that referee: recorded transcripts and the throwaway Forgejo.

**Docs.** Amend testing-strategy 4:
- A fake's domain keeps its own vocabulary. This already holds, and the fake domains are clean.
- A fake's wire face may use the dialect crate's server-side halves, but only where both directions of that shared codec are pinned to real-world transcripts.

**Code.**
1. **The GitHub fake uses the client's half.** It builds `Link: next` with the client's `request::encode` (`skein-fake-forge-github/src/delivery.rs:268`), and its routes carry the client's `plans::tables::Method` (`writes.rs:26`). Give the fake its own (about 30 lines).
2. **Delivery signing is one function used on both sides** (`github::delivery::sign`, called at `delivery.rs:425`). Keep it shared only if a real GitHub delivery transcript checks it. Otherwise the fake gets its own signer.
3. **Run the conformance fact checks against the fake too.** Today they run against the throwaway Forgejo only (fake-forge.md 9). The fake and the real thing should be held to the same facts.
4. **Server-side halves live in the dialect crate everywhere,** in a `server` module that the client never imports. Forge already does this, and llm does in practice; name it so. That this code ships in service binaries does not matter, since the linker drops what a service does not use.

### D2. Test-crate lints

**Call.** Allow `wildcard_enum_match_arm` and `matches!` in test crates.

**Why.** Testing-strategy already says tests are ordinary Rust. The lint costs hundreds of lines of variant lists just to pick one event out.

**Code.**
- Keep exhaustive matches in tests by convention where breaking the build is the point: a referee classifying events, a judge over stories.
- Write every test crate's `[lints]` from one template. Today about 36 manifests carry about 20 variants.

### D3. Limits validity: one name, `valid`

**Call.** Rename the four `check(limits)` functions in the forge family to `valid`; the rest of the tree already has about 30 `valid`s. The return type follows the need:
- `bool`;
- or `Result<(), Why>` where the operator must know which limit failed (forge-setup's design requires the place).

**Docs.** Amend programming-model 6.3 to allow both return types under the one name.

### D4. Test layout

**Call.**
- **In-crate tests:**
  - Default: `src/tests.rs` plus `src/tests/<topic>.rs`, with fixtures in `src/tests/support.rs`.
  - `src/<mod>/tests.rs` only when a test needs that module's private items. That is the one real reason the about 25 such files exist.
  - No sibling `*_tests.rs` files under `#[path]`, and no inline `mod tests {}`.
- **`crates/*/tests/` directories:** move `crates/skein-forge/tests/` (6.6k lines), `skein-fake-forge-protocol/tests/` and `skein-fail-stop/tests/` under `tests/`, as `testing.md:371` already says.
- **Test-crate support:**
  - It goes in the crate's `src/`.
  - Whatever a second test crate uses moves to `testing/`: the TLS world's PKI, the LLM world.
  - No `#[path]` or `include_bytes!` across crate boundaries.

**Docs.** Write this rule into testing.md 6 as the single layout.

### D5. The crate graph: removed from the docs, the filesystem is the source of truth

**Call.** Delete the crate graph from `docs/design/README.md` (section 3). What a crate depends on is what its `Cargo.toml` says; `cargo tree` and `cargo metadata` show it, and no document restates it.

**Docs.**
- Remove section 3.
- Remove per-crate dependency lists elsewhere in the design docs where they restate a manifest.
- Keep the role rules of programming-model 4 ("what a role may depend on"). They are rules, not a copy of the graph, and the manifests must obey them.
- The parts table in section 2 stays, since it says what each part is for. Remove its stale entries:
  - `skein-playground`, which does not exist;
  - "Forgejo's built, GitHub's later", which no longer holds.

**Code.** None. The root `Cargo.toml`'s duplicated fake-crate entries (9 listed twice) are cleaned up as a separate item.

### D6. The loop and referee surfaces

**Call.**
- **`Referee` (skein-world):** give `act`, `next_deadline` and `overdue` defaults, as `starved` and `last_word` already have. Nothing explains why they lack them.
- **`Host`'s policy deadline (skein-shell):** keep `next_policy_deadline` required. `drive.rs` says that is deliberate, and it guards teardown.
- **`Host`'s `next_deadline`:** make it a provided method, the earlier of the mechanism deadline and the policy deadline.
- **Forwarding:** add a forwarding `Host` impl (`Box<H>` or a `Delegate` trait). The about 10 `enum Process` dispatchers in tests then shrink to one accessor.

### D7. Conformance scenarios

**Call.** Add an explicit exception to testing-strategy 10's "one behaviour per test": a conformance scenario may report several observations. Each scenario costs one real-kernel run, so bundling its observations is right.

### D8. Step-code rules: unchanged

**Call.** No change to programming-model 10.
- **Closures and `From`:** both costs can be fixed within the rules. Write inner helpers in the outer error type, and use type shapes that need fewer variant lists.
- **Big enums** (`Role`, `kernel::Error`): adopt one convention. Named category predicates are written once beside the enum and used everywhere, which keeps the build-break property at about a third of the size.

### D9. Before any refactor: `Abort` in both forge components

**Call.**
- **What is missing:** `skein-forge-connection` and `skein-forge-setup`'s host take no `Abort` request, which programming-model 5.2 requires. They also send no TLS close.
- **Now, as a small task:** add `Abort` to both boundaries, since it is a gap against the model.
- **Later:** the TLS close comes with the shared transport (theme 1a).

## Beyond the review: the model, the strategy and the tree

These are my views on the foundations themselves, and on how the tree is laid out. They go further than the per-area findings. They rest on a close reading of programming-model.md, testing-strategy.md and the design index, and on the 13 reports. I did not read every part's design document. jig, smith and temper were not reviewed, apart from a check of which trees depend on which skein crates.

### Overall

**The foundation is unusually strong.** The weak points are in how the code has scaled, not in the ideas.

The programming model is a coherent, well-argued version of the deterministic, sans-io, simulate-everything approach. Several of its choices are better than common practice:
- **One lifecycle everywhere** (5.2): active, closing, closed. Every request gets exactly one terminal event, and components follow the same lifecycle.
- **Flow control as an explicit chain** (section 7): reading is a demand, and each layer refuses at its own entrance.
- **Ceilings instead of a worst case** (6.3). This revision is a pragmatic correction, and it shows the model is used, not only admired.

**The codebase** is good line by line and repetitive across crates. This is the signature of many agents, each building what its task pulled, with no one consolidating afterwards.

### The programming model

**Keep:** sans-io steps, typed handles, owned bytes, the small Rust subset, and fail-stop. None of them turned out to be the real cost (see D8).

**S1. Name the missing tier: a component kit.**
- **The gap.** The role table in section 4 has `lib`, which holds the generic containers, and then the components. Nothing in between holds shared *mechanism*. So each component writes its own:
  - transport (theme 1a, four copies);
  - io stage (1b, 39 sites);
  - lifecycle, pool and earliest-deadline helper (1d).
- **Not a rule problem.** The rules already allow these as concrete, non-generic step machines that a component holds by value. The model just never says that this is the expected shape.
- **Change.** Add a "component kit" role to section 4. Its first members are the transport (`Link`) and the io stage.

**S2. Sanction the half-way state shape, and ratchet the escapes.**
- **The pattern.** Section 5.4 is right, but under pressure large entities drift into structs of flags (theme 2, about 15 places). Allow one shape explicitly: common fields, plus a phase enum whose variants hold the per-phase data. That is what authors reach for anyway.
- **The escapes.** In a step crate, a module-wide `#![expect(...)]` of a subset lint should count as an old form in the gate, one whose count may only fall. kv's store waives five lints for the whole module, in the code where correctness matters most.

### The testing strategy

**Keep:** worlds, seeds that replay, faults in every state, tiny limits, the simulator held to the real kernel by conformance, "fix in the lowest tier", and the starved-run rule. This is the best part of the system.

**S3. One home tier per behaviour.**
- **The gap.** "Each tier makes one more layer real" says which tiers exist, but not which tier owns a behaviour.
- **The result.** Behaviours are tested two to four times: codec at three or four tiers; forge-connection with two harnesses of one tier; doubled harnesses in oauth-accounts and forge-setup.
- **Add a rule.** A behaviour is tested in the lowest tier that can show it. Higher tiers test only what composition adds.

**S4. A harness moves to `testing/` on its second use, enforced.**
- **The gap.** testing-strategy 7 and testing.md 6 already say this, but nothing holds it. Test crates are used as libraries through relative paths, `#[path]` and `include_bytes!` (theme 6).
- **The check.** A gate check that rejects `#[path]` and `include_bytes!` across crate boundaries is cheap.

**S5. Fewer test-shape rules, each checked by a script.**
- **The gap.** Section 10 is good, but it has grown rule by rule, and its breaches are everywhere (theme 4).
- **Change.** A shorter list, where each rule is a gate check, holds better than a longer list held in review. The section already moves a rule into the gate after its second breach; apply that to the rules that are already broken widely.

### Process

**S6. "Built when pulled" needs its counterpart: consolidate when the third copy lands.**
- **The tool exists.** The factory has a ratchet on old forms (`max_out`, `worst_case`, which may only fall). Extend it to duplication signals:
  - io stages written by hand;
  - private `earliest` helpers;
  - full `Limits` literals in tests;
  - socket+TLS stacks written by hand.
- **A periodic review.** Run a cross-crate review like this one now and then, as a factory task. A per-task review cannot see this debt by construction, because each task's diff looks fine on its own.

### The tree: whether to split it

**First take, now withdrawn.** I first suggested moving the forge family out of skein. It is about 181k lines, 38% of skein: the vocabulary, connection, client, setup, three fakes and their worlds. Within this repository only temper depends on it. That reasoning rested on temper being its only consumer. More consumers of forge, llm, kv and the rest are planned, so that argument falls.

**Revised take: a separate tree is not worth it now.**
- **It fixes none of the findings.** The forge family's problems are internal: dialect copy-and-adapt, two harnesses of one tier, flag-struct machines. They move with the code. The cross-crate duplication (the transport, the io stage, the world boilerplate) spans the integrations and the base alike. A split would put two of the four transport copies on each side of a boundary and make them harder to unify.
- **The boundary already holds.** No base crate depends on forge, llm or oauth. Cargo builds only what a consumer depends on, so a new consumer of kv or http pays nothing for the forge's presence.
- **A split has real costs.** It needs another `AGENTS.md`, clippy setup and gate. A change across both sides becomes two changes. In an agent-driven repository, every tree boundary is one more rule set to get right.

**When a split would pay:**
- **Stability promises.** The base ("rarely changes, hard review") and the integrations ("churn with providers and forges") need different stability promises.
- **Gate cost.** The gate runs all of skein's suites for any skein change, and the forge's roughly 80k lines of tests come to dominate the time of a change to lib.
- **A consumer outside the repository.** For example, hearth wants a small, auditable kit, and the 481k-line tree around it makes that hard to review.

None of these holds today.

**S7. Get most of the split's benefit inside skein:**
1. **Name the two layers** in the design README, which is the right place now that the graph has gone (D5):
   - **base:** lib, io, shell, sim, the protocol machines, codec, channel, kv;
   - **integrations:** forge, llm, oauth, ui, and their fakes.
2. **Hold the boundary with a gate check:** no base crate depends on an integration crate.
3. **Scope the gate by layer,** if it is not already: a change to the forge alone need not rerun everything, while a change to lib reruns everything.

### If only three things change

1. The component-kit tier (S1), starting with the shared transport and the io stage.
2. Duplication ratchets and a periodic cross-crate review (S6), so the tree stops growing copies again.
3. The layer boundary inside skein (S7), in place of a tree split.
