# The store's records and versions

This document holds the store's records and version changes, split from [`store.md`](store.md).

## 1. Records and the store version

- **One schema,** in `temper-protocol-store`, with a record for each
  family and for every value those records carry (the client's entries,
  effects, writes, live rows and cached answers; the change's and the
  issues' states; a named call's payload, with the forge's answers and
  errors), generated by skein's generator (skein's `data/codec/README.md`). The
  domain's values translate to and from generated ones by small total
  functions, exhaustive both ways: a domain change to a durable field
  breaks a translation's build.
- **Its generated record code in a codec crate,**
  `temper-protocol-store-codec`, which depends on skein-lib and
  skein-codec alone (skein's `data/codec/README.md`, section 2), so that
  it compiles beside the forge's domain crates rather than after them.
  It holds only the current version's code, `src/generated/store.rs`,
  module `v25`, re-exported at `temper-protocol-store`'s root under
  the same name. Registered values convert at read
  from stored layouts into that codec's layout
  (`floor.md`, 2); no older map codec or patch history is kept.
  `temper-protocol-store` keeps the current schema, owner set and
  translations. `temper-codecs-world`'s drift test compares generated
  records with the codec crate's code. Tests build values, without
  family goldens or generated tests; skein's `every` pins the bytes
  (`skein/docs/design/data/codec/golden.md`, 1).
- **Collections** are pieces or counted lists by jig's rule (jig's
  `protocol/store/records.md`, 1). The schema's limits are made from the
  forge's limits, and checked against the schema's ceilings at start.
- **Settings history room follows the effective core capacities.** Before
  map admission, temper raises the profile's value ceiling to at least
  jig's `sizes::settings_value` (jig's `protocol/store/records.md`, 4),
  and its page ceiling to at least that value plus the profile's key
  ceiling. This includes a whole set of edits, their replaced values and
  the model-name table and the `provider` kind's 16 providers of 64
  endpoints each; stock at the small process deployment's capacities
  needs 40,524,798 bytes. The figure is calculated at startup, never a
  second fixed ceiling that stock growth must update. Checked map sizing
  then derives the opening value, chunk and page from the effective
  limits. The map budget, row count, queues and read slots retain their
  configured bounds. Other records still face the resulting value ceiling.
- **`STORE_VERSION`,** 25, is the version of `temper-store` in jig's
  format row. Its registered layouts change by defaults, former names
  and written jobs, without a version move or patch (`floor.md`, 6).
  At equal levels, the open plans layouts from the store's registry;
  a new registration or pending job upgrades a copy before restoring
  and switching it (jig's `protocol/store/opening.md`, 1.7 and 2).
  A store below the floor, behind the levels or holding values with no
  registry is refused by name, never walked or seeded from code
  (`floor.md`, 4).
- **`temper-store`'s value types** (jig's `protocol/store/layouts.md`,
  2): its `Row`'s variants, one value type per variant its keys hold
  (`store.md`, section 3), each numbered in `temper-protocol-store`'s owner set,
  in its keys' order, and never renumbered. `temper-secrets` is outside
  the registry, fixed at version 1. Family 12 is reserved, outside the
  family's keys. The application's jobs at open are, in this order,
  `test-ids-landing`, `test-ids-receipt`, `test-ids-tier`,
  `test-ids-verification` and `deleted-repository-forge-rows` (below),
  dispatched by `temper_protocol_store::jobs::page`; a name it does not
  know is its refusal.
- **The jobs `test-ids-*`** bring a store written while a failing
  test's id had a ceiling of 4,096 bytes to the binary's ceiling of
  1,024 (below; `../draft/config.md`, 5.2). A narrowed bound is a
  `retype`, which no plan derives (skein's `data/codec/layouts.md`, 2),
  so every older layout of the four value types whose values reach
  `FailingTest` or `TierFlake` is unplanned, whichever build wrote it:
  - **One written job per value type,** each converting its value
    type's unplanned layouts (`Layouts::Unplanned`, jig's
    `protocol/store/jobs.md`, 4) over its value type's ranges:
    `test-ids-landing` value type 20 (`landing`, family 23),
    `test-ids-receipt` 21 (`receipt`, 24), `test-ids-tier` 25 (`tier`,
    28) and `test-ids-verification` 26 (`verification`, 29). They run
    before `deleted-repository-forge-rows`, which reads these families
    through the read edge, at the binary's layout.
  - **The wide text:** the binary's text with `FailingTest.test_id` and
    `TierFlake.test` at `bytes 4096` and the five tier lists of
    landings (below) at `list 759`, the ceilings every older layout
    has, so that each plans to it. A page derives it from the binary's
    text by those seven substitutions, each of a declaration's exact
    words found once; one not found once refuses the page, `why` `the
    binary's text has no single {words}`, which the focused test of
    the binary's text keeps from happening. The job keeps no text of
    its own.
  - **A value's conversion:** its stored layout, the page's
    `JobLayout`, is planned to the wide text at the value type's root
    and variant and converted by that plan; the result is read as a
    generic value of the wide text. Where its ids are all within 1,024
    bytes it is, byte for byte, a value of the binary's layout; where
    one is longer, the rule below changes it, by replacing or removing
    the spans the generic value gives and the counts above them. The
    result is decoded by the generated code at the schema's ceilings,
    which checks it, and put at its key.
  - **The rule,** for a failing test's id past 1,024 bytes: a
    `Failures` holding one becomes `many`, in a receipt
    (`Receipt.failures`, a `ReceiptRow`'s and a `TierRow`'s
    `result`), a verification's blame, a tier record's `failing` and
    a tier goal's `failing`; where a `TierRow`'s `record.failing`
    becomes `many`, each of its posting's landings blamed by index
    into it (`TierPostedBlame`'s `owns` and `suspect`) becomes
    `owns_many` or `suspect_many`; a flake holding one is dropped from
    `TierRecord.flakes`, its count with it, the others kept in order.
  - **Refused,** with the row's key, since relabeling work in flight
    would judge a partial pass as a whole one or post what its pending
    write does not hold: a tier row whose run is in flight
    (`record.run`) holding one anywhere, `why` `a tier run in flight
    holds a failing test's id past 1,024 bytes`; a tier row whose
    posting has a write pending (`posting.entry`) that the rule would
    change, `why` `a tier posting in flight would change for a failing
    test's id past 1,024 bytes`; a landing whose search by test selects
    one (`LandingSelection`), `why` `a landing's search by test holds a
    failing test's id past 1,024 bytes`. The start is refused
    `OpenRefusal::Job`, the store unchanged: its operator starts the
    build before, lets that work end, then this one.
  - **Its counts:** `test-ids-tier`'s `many`, the `Failures` made
    `many`, `flakes`, the flakes dropped, and `posted`, the posted
    landings made `*_many`; `test-ids-receipt`'s and
    `test-ids-verification`'s `many`; `test-ids-landing`, which changes
    no value, none. A store whose ids are within 1,024 bytes, as
    dev.fabrig.ai's are within 256, counts none: each value is put again
    unchanged at the binary's layout.
  - **Once dev.fabrig.ai has run them,** their code goes (`floor.md`, 8).
- **The job `deleted-repository-forge-rows`** drops what a project's
  deletion left naming a repository whose `Repository` row is gone
  (`../draft/deleted-repository-rows.md`), so that the restart's link
  check (`../domain/root-restart.md`, 1.1) meets none of it; the check stays
  strict for everything else. It judges by the store alone, never by
  the deployment's configuration:
  - **Present:** a repository with a row in family 2. **An ended
    forge:** one whose `Forge` row (25) reads ended, or that has none
    while its number is 1 to `ForgeNumber`'s `last` (26): the link
    check's judgement at a start that configures no forge outside its
    records, as every deployment's does.
  - **Exempt,** kept as the link check keeps it: a row of a kind it
    keeps as history (`BranchHead`, `PullState`, `Ci`, `Change` and
    `ChangeCold`, `Issue`, `Application`, `Landing`, `Receipt`,
    `Follow`, `Tier`, `Verification`, `LandingLog`) naming a missing
    repository of an ended forge.
  - **Dropped,** naming a missing repository and not exempt: rows of
    `BranchHead` 6, `PullState` 7, `Ci` 8, the client's `Live` (11,
    variant 0), `Receipt` 24, `Tier` 28, `Verification` 29 and
    `LandingLog` 30, erased whole, each judged by its key; an
    `Application` row (15) whose `Adopted` outcome names one, erased
    whole, judged by its value: a settled answer for a project that is
    gone, whose retry the forge would refuse; and a `Names`
    row (4) loses each resource naming one, put again with the rest, or
    erased when none is left, as a release does. None of these has a
    partner keyed apart from its repository, so pairs go together.
  - **Refused:** any other row the link check judges by a repository,
    naming a missing one and not exempt: `ProposedEffect` 1, `Hold` 3,
    `Subscription` 5, `Entry` 10, the client's `Repository` (11,
    variant 1), `Issue` 13, `Release` 14 (its pending name),
    `Landing` 23 (each
    member), `Follow` 42 and `ChangeCold` 47; they may stand for a
    pending effect, a live owner or a kept answer, and a person clears
    them. The page is refused, `key` the row's and `why`
    `{family} names deleted repository {forge}/{repository}`
    (`Hold names deleted repository 1/20`), so the start is refused
    `OpenRefusal::Job` naming it, the store unchanged.
  - **Its ranges:** families 1, 3 to 8, 10, 11, 13 to 15, 23, 24, 28
    to 30, 42 and 47, in key order; family 12 is reserved. **What it reads:** while each page is out,
    families 2, 25 and 26 whole, through `Store::patch_page` (jig's
    `protocol/store/jobs.md`, 3), bounded by `repositories` and
    `forges`; a row of them that does not decode refuses, naming it.
  - **Its answers** fit `room`: an answer stops
    before a row whose writes would not fit and names `through`; a row
    that cannot fit alone refuses.
  - **Its counts,** in order: `dropped`, then `BranchHead`,
    `PullState`, `Ci`, `Client`, `Receipt`, `Tier`, `Verification`,
    `LandingLog`, `Application` and `Names`: the rows each answer erased of that
    family, `Names` the resources removed, and `dropped` their sum
    (`binaries.md`, 2, prints them).
- **A repository's tag** is its forge's number and its id, packed
  (`../domain/forge/adoption.md`): the tasks' resource parameters and
  saved resources jig keeps name the pair.
- **A forge's record,** the `Forge` family, tag 25 (`store.md`, section 2): its
  number is its key's and its row's, and the number keys every other
  record of the forge, its rows in jig's secrets' store, its
  repositories, its writer and its git identity, so it is never given
  twice: `ForgeNumber`, tag 26, keeps the last given (forge/engine.md, 1).
  Nothing in it is secret (credentials.md, 2.1).
- **The playground's row,** the `Playground` family, tag 27 (`store.md`, section 2
  ), its project's and its account's numbers written as its start
  makes them, so a reset cut by a restart knows what to remove, and the
  reset's step, whose act is sent again at each start until answered
  (setup/playground.md).
- **Bytes 17 and 19** are reserved: no family takes them, and a row
  under either is a tag the decoder does not know (`store.md`, section 3).
- **A deployment made again** when its named refusal requires a fresh
  store (`floor.md`, 4):
  remove each forge from the client, which erases its credentials and
  removes its box group and directory (forge/engine.md, 3); stop temper,
  move `active`, `generations/` and `transcripts/` aside together in
  the deployment's directory that jig's `deployment` member names
  (configuration/README.md, section 2; jig's `protocol/store/README.md`, section 2),
  and start afresh, a first start (configuration/startup.md, section 1). What
  survives:
  - the configuration and its private files, which no store holds;
  - no forge: each is set up or connected again, numbered afresh in the
    new store (forge/engine.md, 1);
  - nothing else: jig sweeps its own secrets the new store names none
    of, so LLM accounts are signed in again (jig's `protocol/store/secrets.md`
    ); owners and projects are seeded again from `engine`, and
    each repository is adopted again through the client
    (configuration/startup.md, section 1); tasks, goals and temper's families
    stay in the store moved aside, and the deployment's id is drawn
    again, so its branch namespace is new.
- **Sizes.** `temper-protocol-store` computes, from the forge's limits,
  the largest key and the largest value of its families, and hands them
  with `STORE_VERSION` to jig's component, which checks them with its own
  against skein-kv's limits, and the start is refused when they do not
  fit (jig's `protocol/store/records.md`, 4).
  `temper-service` builds
  `jig_protocol_store::sizes::Commits { in_flight: root.journal.commits, writes: root.journal.writes }`
  for the store's sizing check and commit edge. The real-loop world uses
  the same inputs. The journal's limits are temper's own decision
  `Limits` (`../domain/root.md`, section 9); temper names no skein
  `JournalLimits`.
  The service derives the shared store and secrets page byte bound as
  `P = max(K + V, F(A))`, where `K` and `V` are the checked map sizes and
  `A` is `root.loads.transcript_bytes`. Startup checks that `A` covers
  the agent's largest ordinary turn; the hub's turn cap is not its value.
  `F(A)` uses the current generated `core_v6::TurnRecord` worst-case
  encoding with a copy of the existing codec limits, changing only its
  transcript field bound to `A`, plus the actual 12-byte frame wrapper.
  Out-of-codec `A`, arithmetic overflow, or a page beyond the profile's
  ceiling refuses admission rather than clamping. Jig's canonical
  `jig_protocol_store::sizes::frame` owns this current full-frame sizing.
  Page bytes are an admission counter, not an allocated page pool: this
  changes the priced bound and may admit more data-dependent occupancy,
  while page rows, chunk and frame decoder capacities, queues and read
  slots stay the same. Existing request byte budgets still apply.
  Before any commit data IO, jig checks each actual encoded frame against
  `P`, admitting equality and refusing the entire batch if any frame is
  larger, even a later turn after other prepared writes. Its in-process
  `FrameTooLarge { number, task, bytes, limit }` is the rejected commit's
  only terminal. Temper feeds that number through the existing root
  `Uncommitted` policy and stops with the named service cause. The host
  prints, with its normal newline:

  ```text
  temper-box serve: commit {number} refused: task {task}'s transcript frame, {bytes} bytes, past the store's page of {limit} bytes
  ```

  Earlier durable data is recoverable; the refusal changes no stored or
  wire format.
- **Every other failed commit says why.** The engine stops with
  `Stop::CommitFailed { number, why }`, `why` a `CommitStop`: either
  `Store(CommitFailure)`, the store's cause as jig's
  `protocol/store/commits.md`, 1 gives it, or `Route(RouteStop)`, the
  engine's store routing stopping on its own with `number` the last
  commit it routed. The routing hands up `Up::Failed { number, why }`
  for both, and the engine feeds `number` through the root's
  `Uncommitted` policy, as for `FrameTooLarge`, before it stops. Nothing
  else changes: the engine still stops at a failed commit, and nothing
  stored or on a wire carries `why`. `RouteStop` is `Open` (the store
  answered a refused open while the engine ran), `Secrets` (the store
  answered its secrets not ready), `Cursor` (a load's continuation did
  not translate into its cursor, or did not advance) or `Page` (a load's
  page past the start could not be measured or cut). The host prints,
  with its normal newline:

  ```text
  temper-box serve: commit {number} failed: {why}
  ```

  `{why}` is bounded, at most 160 bytes, with no record's contents. Its
  byte and entry figures are grouped in threes with commas
  (`268,435,456`); the commit numbers are plain:

  | `why` | `{why}` |
  |---|---|
  | `Store(Refused(Full(Budget { used, budget, projected })))` | `the store's map is full ({used} of {budget} bytes; this commit needs {projected})` |
  | `Store(Refused(Full(Entries { capacity })))` | `the store's map is full ({capacity} entries)` |
  | `Store(Refused(Full(Numbers)))` | `the store's commit numbers are at their end` |
  | `Store(Refused(TooLarge(Key)))` | `the store refused it: a key past the key limit` |
  | `Store(Refused(TooLarge(Value)))` | `the store refused it: a value past the value limit` |
  | `Store(Refused(TooLarge(Ops)))` | `the store refused it: more operations than the commit limit` |
  | `Store(Refused(TooLarge(Frame)))` | `the store refused it: a frame past the commit limit` |
  | `Store(Refused(TooLarge(Page)))` | `the store refused it: a page past the page limit` |
  | `Store(Refused(TooLarge(Range)))` | `the store refused it: a range that ends before it starts` |
  | `Store(Refused(TooLarge(Record)))` | `the store refused it: a log's record past the record limit` |
  | `Store(Refused(TooLarge(Log)))` | `the store refused it: a log past its length limit` |
  | `Store(Refused(Busy))` | `the store refused it: its queue is full` |
  | `Store(Refused(Unavailable))` | `the store refused it: the store is not open` |
  | `Store(Refused(Logs))` | `the store refused it: a log's operation its log rule refuses` |
  | `Store(Failed)` | `the store's log failed a write or a sync, so its outcome is uncertain` |
  | `Store(Owner { owner })` | `the store committed root commit {owner} as its commit {number}` |
  | `Store(Transcript)` | `a file step of its transcripts failed` |
  | `Store(Check(CHECK))` | `the store's own check refused it: ` and CHECK's words, below |
  | `Store(Stopped)` | `the store had stopped at another commit's failure` |
  | `Route(Open)` | `the engine's store routing stopped: the store refused to open while the engine ran` |
  | `Route(Secrets)` | `the engine's store routing stopped: the store's secrets were not ready` |
  | `Route(Cursor)` | `the engine's store routing stopped: a load's cursor did not translate or advance` |
  | `Route(Page)` | `the engine's store routing stopped: a load's page could not be measured or cut` |

  CHECK's words: `Number` `its number is not the store's next`, `Closed`
  `the store is not open`, `Queue` `the queue behind transcripts' syncs
  is full`, `Writes` `more writes than the root's bound`, `Switching` `a
  patch switch is pending`, `Encoding` `a key, record or frame past its
  codec's limits`, `Copy` `a copy's first key is not in the map`, `Reads`
  `a read of the map it needs failed`, `Capacity` `more operations than
  the commit's bounds hold`, `Bytes` `its operations past the store's
  commit bytes`. So the deployment that stopped at a full map prints
  `temper-engine serve: commit 685204 failed: the store's map is full
  (268,433,350 of 268,435,456 bytes; this commit needs 268,435,862)`.

A stored open question's whole words and a held answer's words each have a
schema ceiling of 65,536 bytes. Their runtime bounds, `open_words` and
`held_answer`, both come from `forge.client.op_bytes`; the start refuses a
bound above the ceiling by the ordinary schema-bound check (2026-11-04).

A named call's `TooLarge` keeps its excess (skein's `forge/vocabulary.md`, 1.4):
`Error`'s `too_large` carries an `Excess` record, its `bound` an enum of
the five bounds and `limit`, `size` and `exact` beside it.

A tier's stored goal-branch list has a ceiling of 256, sorted by goal number
with no duplicate. Its runtime bound is `forge.holds`; a value above 256
refuses the start. The ceiling keeps the tier row's worst-case encoding,
including each goal's failing-test IDs, within the codec's u32 length
envelope (2026-11-04).

A tier's lists of landings, its pending landings (`TierRow.pending`), a
run's (`TierRun.landings`), a finding's blamed ones
(`TierFinding.blamed`), a probe's waiting groups (`TierProbe.waiting`)
and a posting's landings (`TierPosting.landings`), each have a ceiling
of 1,537. Their runtime bound is `2 * forge.changes + 1`, so
`forge.changes` is at most 768, the least of the five ceilings less one,
halved, and a value above it refuses the start, naming `forge.changes`
and that bound before the store's sizing runs
(`configuration/limits.md`). A list encodes its count; a smaller
bound's bytes read unchanged through the registry, so the widening from
759 is derived.

Failing-test and flake ids (`FailingTest.test_id`, `TierFlake.test`)
have 1,024-byte ceilings: worst-case tier rows fit the codec's u32 length
envelope at 1,537 landings (~1.9 GB, mostly a finding's blamed landings'
failures). 4,096-byte ids exceeded it past 759 landings (4,294,744,175
bytes at 759), pinned by `temper-protocol-store`'s focused test. Runtime bound
`forge.tiers.test_id_bytes` is stock 512, a finding signature's id
capacity, within both ceilings (least: 1,024). Start refuses values
above 512, naming setting and bound before store sizing
(`configuration/limits.md`); a focused test pins the signature bound
within the ceilings. `test-ids-*` jobs (above) bring 4,096-written stores
within bounds. Receipt report keys (`ReceiptTest.key`) retain their
4,096 ceiling: no tier row holds them. Runtime bound `test_id_bytes`
also keeps stored keys within 1,024.

Tier failing-test and flake lists (`FailedTests.tests`,
`TierRecord.flakes`, `TierFinding.flakes`, `TierTests.tests`, gate
selection's `LandingSelection.tests`, receipt's `ReceiptTests.tests`,
among others) each have a 1,024 ceiling. Runtime bound
`forge.tiers.failing_tests` is stock 64, start-checked against a finding
signature's 64 ids (`configuration/limits.md`). Lists encode their
count: tier rows written at smaller bounds (including 16) read unchanged
through the registry at 64; the raise moves no version and brings no patch.

A repository's stored CI workflows, the record's `workflows`, are a list
with a ceiling of 16 names, each of at most 255 bytes: its bounds are the
forge's constants `WORKFLOWS` and `WORKFLOW_BYTES` (`../domain/forge/adoption.md`,
7), not configured, and the schema's ceilings equal them.

A repository's stored landing branch, the record's `landing`, has a
ceiling of 4,096 bytes and the runtime bound `forge.name_bytes`, as the
adoption's `landing` has; added with the default `0x`, it reads empty in
a record written before it, and the decoder takes that record's
`settings.default_branch` for it. An adoption's kept outcome,
`ApplicationAdopted`, carries the same `landing`, empty in an outcome
kept before it (`../domain/forge/adoption.md`, 8).

A named call's comparison answer is names and counts (skein's `forge/vocabulary.md`, 1.3): `CompareAnswer` holds `before`, `after`, `ahead`, `behind`, `files`, a list of at most `forge.client.rows` paths, and `changed`.

A listing's page of items says whether it was cut at the answer's bytes (skein's `forge/forgejo.md`, 1.3): `ItemsAnswer` holds `items`, `more`, `now` and `cut`, so a stored answer read after a restart pages on from its last kept row as an answered one does (skein's `forge/client.md`, 4, "Paging") (2026-11-11).
