# chat-reading: status

2026-11-06. Where the design lags or departs from [chat-reading.md](chat-reading.md).

- **Design departs:**
  - 5: *Keys, in the terminal:* `../client/README.md`, 5.15: the terminal reads lines, never raw keys. `up` and `down`, or the escape sequences PgUp and PgDn make, followed by Enter, read earlier or later lines and print the whole window again. The plan `chat-reading-c` decided, under its request's "take the nearest thing".
  - 5: *Keys, from anywhere on the page:* skein's `ui-web.md`, section 7: a component holding the focus keeps PgUp and PgDn as well, beside the menu or dialog the section excepts, since a component's keys are its own. The plan `chat-reading-c` decided.
  - 5: *The same rule opens a chat:* `../client/README.md`, 5.15: in a browser it holds. The terminal opens on one page, since a shell with no view measures nothing, and `up` reads the next. An empty page with an older cursor reads on, so that it isn't stranded. The plan `chat-reading-c` decided, under its request's "take the nearest thing".
  - 5: *The newest are never lost:* jig's `client/domain/client.md`, section 10: the lines that go are those furthest from the page just read, not from where the person reads, since a thread measures no view. A window holds far more than a screen, so what goes lies out of view either way; seen by reading. The plan `chat-reading-c` decided.
  - 5: *"Latest ↓":* `../client/README.md`, 5.15: on an agent's page, the person sending does not go to the end, where the section has it: its log has no end request, which a chat's page alone counts. A press there reaches the end a page at a time, the log following, where a chat's reads the end at once. The plan `chat-reading-c` cut an agent's page out of the pill, `chat-reading-b` landed one on it, and the close took what was built. No reason is recorded for sending.
  - 5: *A window bounded by size:* `../client/README.md`, 5.4 and 5.15: `lines` stays for jig's reference UI and tools, whose trees are priced by rows. temper sets it to `document_bytes / LINE_ROOM`, 16,384, past what its bytes hold, so it never bounds the conversation first. The plan `chat-reading-c` decided, taking the draft's alternative.
  - 5: *In every browser:* `../client/README.md`, 5.15: the browser tier runs Chromium alone, including the position story with `overflow-anchor: none`, the nearest a run comes to Safari. Firefox and Safari themselves are read, not run; the user reads the position staying put on a real chat. The plan `chat-reading-c` decided, under its request's "take the nearest thing".
  - 2: *Its time:* `../client/README.md`, 3.5: a committed turn says only when it ended, so a run is measured from the line before its first turn, which a run of one turn has too; at a window's head or for a turn's second run, from its first turn's end, often no time at all. It holds the model's writing of any text that opened the turn. Storing a turn's start would change a stored format and a protocol (`../client/README.md`, section 11). The plan `chat-reading-b` decided, under its request's "take the nearest thing".
  - 2: *A failed call:* `../client/README.md`, 3.5: "1 failed" stands in the line's description, before the time, not after a comma in its name, so the time takes the signal's colour with it, where this section has ", 1 failed" alone in that colour: skein's summary holds one name and one description. While a run is out its description is the call under way, so the line says no "1 failed" until it ends, where the draft has the same line add it; no reason is recorded. The plan `look-round-6` decided.
  - 2: *A run's end:* `../client/README.md`, 3.5: a document's write ends a run too, and any other drawn line: its line stays where it falls, so a run can't span it without moving calls past it. The plan `look-round-6` decided.
  - 2: *A row a call:* jig's `client/domain/view.md`, section 9: jig's reference UI keeps a folded line a call. It knows no tool's words, and a chat's line is temper's view. The plan `chat-reading-b` decided.
  - 2: *What stays apart:* `../client/README.md`, 5.9: on an agent's page a `delegate` call is a row in a run and counts in it, since a delegation's card is the chat's. The plan `look-round-6` decided.
  - 2: *The terminal:* `../client/README.md`, 3.5: a print has no opening, so the terminal prints a run's rows under its line whatever its state, a row a call, where the draft has them opened: there a run is more than one short line. No reason is recorded. The plan `look-round-6` decided.
  - 3: *Drawn once:* `skein/docs/design/ui.md`, section 10, and `../client/README.md`, 3.5: the page reads the whole text again at each delivery, and a closed block's nodes come out the same, so it stays on the page unchanged. Nothing keeps a block read. The whole tree is rebuilt at each delivery as it is for any change, and a block kept apart would be a new mechanism for no sight of difference. The plan `chat-reading-a` decided, under its request's "take the nearest thing".
  - 3: *Whole:* an answer past the engine's retained bytes (`views.text_bytes`, 65,536) arrives whole only to a page following it from its start; a page opened later shows the retained end until the turn commits. One delivery's wire field stops at the same 65,536, so holding more needs a chunked delivery (`../client/README.md`, section 11). The plan `chat-reading-a` decided, likewise.
  - 4: *The order changes:* jig's `client/domain/client.md`, section 14: an outcome's line comes before inputs, not after them. A note's input can fill the budget, and the chat's document line and "Show" read that call's outcome. An outcome's line is bounded by `text`, so it costs the input little. The plan `chat-reading-a` decided, under its request's "an outcome's first line breaks a card".
  - 4: *A delegate's card:* jig's `client/domain/client.md`, section 10: every result's summary stays whole, priced last, not only those a card reads: the transcript knows no tool's words, and a whole summary is what the agent's page, the tools and a brief read. The plan `chat-reading-a` decided, likewise.
  - 4: *Whatever their results weigh:* jig's `client/domain/client.md`, section 16: a turn past `document_bytes` on the wire (1,048,576 bytes) reads as too large, with no calls' names. Reading it needs a page past the client's document bound (`../client/README.md`, section 11). The plan `chat-reading-a` decided, under its request's "take the nearest thing".
- **Open:**
  - 7: the line's verbs and a run's time as `../client/README.md`, 3.5, has them, to be read by the user on a real chat; section 11 there holds each default.
