# agent-kinds: a run reads and proposes every kind a settings file names

## Goal

A run's `settings` read and `propose_settings` name the kinds a settings file names
(temper's `domain/agent.md`, 8.1, "The kinds it reads and proposes"): jig's `charter`,
`template`, `policy`, `rules`, and temper's `landing-rule` (with `project`) and
`forge-charter`, and `project-policy` (with `project`). `propose_settings` already decodes
them all through `settings_form::file::proposal_items`; its schema and the read's do not say
so, and the read refuses them. A read of temper's kinds is answered with the value the forge
keeps, as ctl's `settings show landing-rule` is.

Acceptance:

- The `settings` and `propose_settings` schemas (`calls.rs`, `SETTINGS_SPEC`'s neighbours at
  the `settings` and `propose_settings` specs) give `setting.kind` the enum `["charter",
  "template", "policy", "rules", "landing-rule", "forge-charter", "project-policy"]` and a
  `project` member, `{"type":"integer","minimum":1,"maximum":4294967295,"description":"For a
  landing rule, its project, the deployment's when left out; for a project's policy, its
  project."}`; each description within the host-tools bounds (`domain/agent.md`, 4.3: a
  tool's at most 160 bytes, a member's at most 120); `temper/docs/help/reference/host-tools.md`
  regenerated by its test's writer (`SKEIN_CODEGEN_WRITE=1`; the stated `docs/help/`
  departure: the page is rendered).
- `settings::read` decodes those kinds into the core's settings as
  `settings_form::kinds::setting` and `file.rs`'s `setting` do for a settings file
  (`Setting::Application { kind: 1 | 2 | 3, scope, number }`, `Setting::ProjectPolicy {
  project }`), refusing `project` on any other kind as `Problem::Range(b"project")`; reuse the
  form's decoding, never a second copy of it.
- The root answers a run's read of an application setting at the newest revision with the
  core's document and the forge's value (`domain.forge.setting(kind, scope, number)`, as
  `route/kinds.rs` reads it for ctl), rendered through the same text as ctl's (the settings
  form's value of that kind); at a held revision, as the core answers it. The family check
  stays the core's: a run whose authority lacks the settings family is refused as today.
- A run's read of a project's policy is answered as the core answers it today (unknown): the
  design's gap, recorded below.
- Step tests in `temper-engine-smith/src/tests/settings.rs`: each kind decodes, with and
  without `project` where it takes one, and `project` on a charter is refused. A story in
  the engine's domain world, `temper/tests/engine/domain/tests/suite/agent_reads.rs`,
  `a_run_reads_a_landing_rule_and_the_forges_charter`: a chat whose authority holds the
  settings family (a world's own defaults, as `settings.rs`' stories give them) reads
  `landing-rule` (the deployment's rule 1) and `forge-charter` 1 and hears each value, within
  the answer's bound.
- temper's `docs/design/domain/agent.status.md`, its first Not yet entry: the sentence "8.1:
  a run's `settings` read and `propose_settings` schema name jig's four kinds alone, not
  temper's kinds or a project's policy (`temper-engine-smith/src/settings.rs`, `calls.rs`)."
  removed; the entry's second sentence, a project's policy read, stays (no task of this plan
  builds it). Edit only that entry: `stock-configuring` edits the next one.
- The focused tests of `temper-engine-smith`, `temper-engine-domain` and the engine's domain
  world, and `temper`'s `commands` tests (the `host-tools` page), pass.
