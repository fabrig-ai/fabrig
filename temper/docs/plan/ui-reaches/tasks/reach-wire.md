# The records: `ProjectClasses` and `Reach`

## Goal

The client wire gains the records of a project's classes and of a reach, and the store gains the classes and a `SettingValue` variant for them, so that kind 8's value and a decision's reach have their encodings before anything reads them (`temper/docs/design/protocol/configuration.md`, 13.2; `temper/docs/design/domain/forge.md`, 5.10). Additive: no existing record changes.

Acceptance:

1. `client-wire-v1.schema` holds the records of `temper/docs/plan/ui-reaches/notes/contracts.md`, section 2, exactly as written there, after `ProjectWays`, under the comment it gives.
2. `store-v11.schema` holds `ReachKind`, `ReachClass`, `ReachKindOf`, `ReachSet`, `ClassSubject`, `ClassItem`, `PathSet` and `ProjectClasses`, as the wire's, beside its `ProjectWays`; `SettingValue` gains `classes: ProjectClasses` as its last variant, so no earlier variant's tag moves.
3. Both crates' generated code and goldens are regenerated by the drift test (`notes/common.md`, *Generated files*), and `heavy cargo nextest run -p temper-codecs-world --test suite -E 'test(drift::)'` passes without `SKEIN_CODEGEN_WRITE`.
4. The store's settings codec (`temper/crates/temper-protocol-store/src/records/settings.rs`, `decode`) answers a stored `SettingValue::Classes` as `Undecodable`, since the forge has no value for it yet (`classes-value` gives it one); a comment says so in the design's words, citing 13.2.
5. Rows, no new test function:
   - in the wire's `limits_take_each_bound_from_its_source_field` (`temper/crates/temper-client-protocol-wire/src/tests.rs`), or the nearest existing table of record bounds there: a `ProjectClasses` at every bound accepted and one item past `items` refused, and a `Reach` round trip; if no table fits, the generated goldens alone, said in the report;
   - none in the store's tests: the round trip of a classes value needs the forge's value, and `classes-value` adds that row.
6. Readers: the new records have none, and no reader of an existing record changes. A compile-forced arm elsewhere (an exhaustive `match` on the store's `SettingValue`, such as the codecs world's fuzzy store test) answers as acceptance 4's arm does, named in the report.
7. Runs, counts in the report: `heavy cargo nextest run -p temper-client-protocol-wire -p temper-protocol-store`; the drift test of acceptance 3; `heavy cargo check --tests -p temper-engine-domain-forge -p temper-engine-smith -p temper-service -p temper-client-domain -p temper-client-tools -p temper-settings-form -p temper-codecs-world`; `heavy cargo clippy -p temper-client-protocol-wire -p temper-protocol-store --all-targets -- -D warnings`.
8. Status: delete the **Not yet** entry naming `ui-reaches/reach-wire` in `temper/docs/design/protocol/configuration.status.md`.

## Owns and may change

Owns the two schemas' new records and `SettingValue`'s variant, their generated code and goldens, acceptance 4's arm and 5's rows, and the status entry. Not `settings_kind` (`classes-kind`'s), not the forge's `Value` (`classes-value`'s), not any existing record.

May change, compile-forced only: an exhaustive `match` on the store's `SettingValue` or a hand-built ceilings literal in any crate of temper's tree, each given the arm or field the new variant or list needs and named in the report.

Options, each decided:

- **The generator names a part differently** from the contract (`PathSetParts`, a list's ceiling field): take the generator's, and say so.
- **A golden the drift test writes outside the two crates' `golden/` directories:** it is generated by the same test; keep it and name it.
