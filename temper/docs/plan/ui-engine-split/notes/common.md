# ui-engine-split: rules every task keeps

- **The request** is `temper/docs/plan/ui-engine-split/inputs/request.md`:
  milestone M2 of `temper/docs/design/draft/deployment-binaries.execution.md`,
  the engine's half of the draft's sections 4 and 9.2. Read it for the
  why; your spec and the design sections it names are what you build.
  `temper/docs/plan/ui-engine-split/notes/contracts.md` holds the shapes
  that cross tasks: build to it, never around it.
- **The box and its tests don't change.** The box's `temper` keeps every
  command it has, its words, help and exits. A task that moves code out
  of a crate leaves its old callers calling it through the new crate,
  not through a copy; no behaviour moves with it unless the spec says
  so.
- **A move is a move:** the moved items keep their names, signatures and
  doc comments, and their tests move with them, unchanged but for paths.
  A test that only pinned where an item lived is cut.
- **The worker's side keeps composing as today** (the box and the tests
  run engine and worker in one process). Building `temper-worker` is M3's,
  not this plan's.
- **Tests stay cheap:** a new case of one behaviour is a row of an
  existing table test. No test reaches a real host, a real forge or a
  real LLM; the worlds' fakes stand in. temper's focused and fuzzy suites
  go to 30 and 120 CPU seconds in the gate: a new test binary costs its
  link, so a new package's step tests are one test binary.
- **Only the focused and fuzzy suites run.** Never `tools/tiers/run`, a
  `<tier>-<tree>` profile, `scripts/browser.sh`, a browser, process or
  live tier story, nor a walk, render check or throwaway driver. A
  slow-tier test your change makes stale is updated, compiled (`heavy
  cargo check -p PKG --tests`) and named in the report.
- **Every build and test through `heavy`,** with `TEMPER_BUNDLE=none` (the
  machines' cargo config sets it). `cargo tree`, `cargo metadata` and
  `cargo fmt` build nothing and run directly.
- **A new crate** takes its lint profile with `python3 -I -B
  tools/lints/lints.py --set PACKAGE PROFILE` (`tools/lints/design.md`,
  3: `step` for a crate under the subset, `binary` for a binary's
  package) and its tree's `clippy.toml` variant as that tool says; its
  member line in the root `Cargo.toml` goes after the line your spec
  names, its `[workspace.dependencies]` line likewise, so that tasks
  adding crates beside yours touch other lines.
- **A stored format, a protocol or a public interface may change freely**
  (no compatibility, the user, 11-06): none is expected here; say so in
  the report if one moves.
- **Not yours:** `docs/design/` (this plan's design is the contract; what
  the code taught goes in the report) but a status entry your spec hands
  you; the drafts; `docs/help/` but a generated page your change makes
  stale (`docs/help/reference/*`), regenerated by its own tool, never by
  hand.
- **Before calling a focused or fuzzy failure "outside the change",** run
  it once on the pristine base. If main passes and the branch fails, it
  is the branch's.
