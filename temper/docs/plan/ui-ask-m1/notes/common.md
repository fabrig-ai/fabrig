# ui-ask-m1: what every task holds to

- **Focused and fuzzy alone.** Never `tools/tiers/run`, a `<tier>-<tree>` profile,
  `scripts/browser.sh`, a walk, a render check, a screenshot or a throwaway driver. A
  story in a slow tier (browser, process, live) is written and compiled
  (`heavy cargo check -p PKG --tests`), not run: say so in the report.
  `temper-client-journeys again` is generation, not a walk: a task whose change leaves a
  journey's recording stale runs it (retry up to three times on "a key mark caught a
  moving page", each on a fresh fake box).
- **Tests stay cheap.** temper's focused and fuzzy suites go to 30 and 120 CPU seconds in
  the gate, and a plan that adds cost is rejected there. A new case of one behaviour is a
  row of the existing table test the spec names; a new test is only one the spec
  sketches, in a world below the real loop, beside its siblings' fixture. No test reaches
  a real host or a real program.
- **The failing test first.** Write the spec's rows, run them, see them fail for the
  rule's reason, then build. The report quotes the failure seen.
- **A new test must bite** (the implementer's text): break the rule once by hand, see the
  row fail, restore.
- **The shapes are `temper/docs/plan/ui-ask-m1/notes/contracts.md`'s.** A name, field,
  number or word it gives is spelled as it gives it. One it doesn't give is yours, inside
  your files.
- **The configuring chat stays as it is:** charter 3, template 3 and
  `temper/crates/temper-service/src/stock/configuring.txt` are not edited, and what its
  runs are declared and do is unchanged, unless a spec says otherwise. Its tests
  (`temper/tests/engine/domain/tests/suite/configuring.rs` and the stock tests on charter
  3) keep passing as they stand, but for a line a spec names.
- **No compatibility before v0.1.0.** A stored format, a protocol or a public interface
  may change; a spec that changes one says so, and the report names it.
- **Generated files your change makes stale are yours,** regenerated by their own tool
  (`SKEIN_CODEGEN_WRITE=1` with the test that writes them; `temper-client-gallery`;
  `temper-client-journeys`), never by hand, and named in the report with what moved:
  `temper/docs/help/reference/host-tools.md` by `temper/crates/temper/src/tests/commands.rs`
  (`the_page_host_tools_is_what_the_declarations_render`),
  `temper/docs/help/reference/settings-fields.md` by
  `temper/crates/temper/src/tests/settings_fields.rs`, terminal goldens by
  `temper/crates/temper-client-shell-terminal/src/tests/render.rs`. Goldens, prints and
  the gallery's `names.txt`/`tests.rs` conflict across plans: on a catch-up, regenerate
  rather than hand-merge, and keep `names.txt` sorted as it is.
- **Help pages** (`temper/docs/help/`) are read by tests (`.config/gate/read-by-tests.txt`):
  a page your change makes wrong is yours to correct within its bound (12,288 bytes for
  a concept page, 32,768 for a reference page), never raising it, and named in the report.
- **`temper.css`:** new rules go under `/* ==== ui: settings ==== */`, never at the end of
  the file; replaced rules are removed where they stand.
- **`docs/design/` stays closed** but for the status lines a spec says to delete, as a
  stated departure from the implementer's text: the design is written, and its status
  must say what is built when the branch lands. What the code taught goes in the report.
- **Before calling a focused or fuzzy failure "outside the change",** run it once on the
  pristine base. If the base passes and your branch fails, it's yours.
- **A test's oracle or helper that your change's correct behaviour trips is yours** to
  repair in the same task, keeping what it checks for everything else, and named in the
  report.
