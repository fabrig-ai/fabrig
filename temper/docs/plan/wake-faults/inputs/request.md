# wake-faults: invalid attempts that say nothing, and a parked goal woken again and again

A goal on a real deployment, at fabrig `7638040201`, met three faults in its runs, and the third recurred at `b4555e6785` (many short activations of a parked goal, each recording the same message as its reason, some saying nothing needs a decision). They cost about 29 minutes of active time between them, and none was diagnosed from the outside. Their evidence is outside this repository, so the words here are what you have. A failed run's end has since gained its invalid reason (`RunEndFailed`, on main), so start by reading what that reason would have said. **Run, unless marked read.**

## What's wanted, ranked. Drop from the bottom if it passes five tasks, and say what you dropped

1. **A goal's first run ends invalid after successful reads.** (Since then a cause was found and fixed: `program-burst-files`, a private-file event reaching the wrong program backend under parallel `sub_agent` calls, which aborted the agent and read as invalid. Check first whether these three attempts were that; if so, drop this item and say so.) Three attempts of a goal's first run, on Claude Code at xhigh, ended failed, class invalid, after 31, 21 and 37 recorded turns. Each one's last call was a successful shell read, and run-ended came 62, 91 and 51 s after it. A fourth attempt, a fresh run, finished the cut. Find what makes a program-backed run's result invalid after a turn that succeeded: the adapter reading the program's last output, a turn past a bound, the program exiting without a result, or a timeout read as invalid. The failing test first, at the lowest tier with smith's program backend and a scripted program. Fix the cause, or if the program truly gave no result, have the end say so.

2. **A repair's attempts end invalid in under a second, with no turn.** A CI repair's four attempts on Sol at high all ended invalid, with no decoded turn, no model use and no spend: the first after 17.9 s, the rest after 0.58, 0.25 and 0.20 s. The task was then held at invalid count 4 past its allowance of 3. Find what an attempt does before its first turn that can end it invalid, and why it repeats at once. The failing test first. An attempt that never reached its model shouldn't spend the task's invalid allowance as if the model gave a bad result: say how it should be classed, in the design's terms, and make it so.

3. **A parked goal wakes again and again on an escalation it has already passed to its person.** A goal's lead passed a held repair's question to its person through a person task, and waited. For three minutes, 19 activations each woke on the same message, an escalation still waiting for the goal's decision, inspected the same held repair or the pending person task, made no decision, and parked again, a run's cost each time. **The rule, settled:** if a part of the ended run covered the entry's kind and the run left it undecided, the entry doesn't wake the task again by itself. It's offered at the next wake, whatever wakes it, and wakes the task only when it changes, by a new revision or a message about it. If no part of the ended run covered it, it wakes the task again, as now (`temper/docs/design/draft/per-wake.md`, section 4, an entry reaching the cut). It belongs in jig's `domain/tasks.md` 8.6. The failing story first, a row of jig's per-wake story table, with both cases.

4. **The design says so:** `per-wake.md`, section 4, and jig's `domain/tasks.md`, wherever the undecided entry's wake is written, and the invalid class wherever a failed attempt's classes are.
