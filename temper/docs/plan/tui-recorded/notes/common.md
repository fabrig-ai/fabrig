# tui-recorded: what every task holds to

- **Focused and fuzzy alone (`AGENTS.md`, 5; the user, 11-06).** Never `tools/tiers/run`, a `<tier>-<tree>` profile, `scripts/browser.sh`, a browser, process or live tier, one of their stories, a walk, a render check or a throwaway driver, even where a test's name invites it. A new story for a slow tier is written and compiled (`heavy cargo check -p PKG --tests`), not run, and the report says so. Recording a journey again (`temper-client-journeys again`) is generation, not a walk: the one task whose spec names it runs it.
- **The contract is `temper/docs/plan/tui-recorded/notes/contracts.md`.** Its names, fields, signatures and records are binding. A change it seems to need is a question; a detail it leaves open is yours, named in the report.
- **The design is written:** `temper/docs/design/client/README.md`, 6.13, 6.14 and 7.1 (the TUI's flow), `temper/docs/design/client/tui/journeys.md` (the TUI's journeys), and `temper/docs/design/client/journeys.md`, 3.2, 3.6 and 3.7 (the shared file, redaction and scan). `docs/design/` stays closed to you: what the code taught you goes in the report.
- **No secret in a print or a log.** The approval's secret, a printed link's secret and every credential are `skein_lib::Secret` wherever the TUI holds them, whose `Debug` gives only a length. A recording keeps them only as the design says, in the person's private file; nothing logs a recording's line. Tests use fake bytes built in the test (`[7; 32]`, a fixed seed, a token's shape built from pieces), never a real secret, and reach no real host or account.
- **A rule's tests carry the plan:** where your spec says "red first", commit the failing test, then the code that makes it pass, so the branch's history shows it red; the report names what each failed on.
- **Tests stay cheap.** A new case of one behaviour is a row of an existing table test (`skein/docs/foundation/testing-strategy.md`, 8); a story goes beside its siblings' fixture. No fuzzy test. Budgets and timeouts are the user's, never raised. Name your new tests' times in the report.
- **A compiler-forced arm or field** your change makes in another crate (a match on `Told`, `Report`, `Kind`, a literal `Settings`) is yours, in any tree, edited only for that, with the nearest existing behaviour. List each in the report.
- **Generated files** your change makes stale (goldens your spec names, prints, `docs/help/reference/*`, counted baselines) are yours to regenerate with their own tool; a golden this plan's spec asks you to write by hand is written by hand and read against the design's lines.
- **A test's oracle or helper that your change's correct behaviour trips is yours to repair,** keeping what it checks for everything else, and named in the report.
- **Before calling a focused or fuzzy failure "outside the change",** run it once on the pristine base. If the base passes and your branch fails, it's yours.
- **Overlaps:** the browser's journeys (`temper-client-shell-web`'s `journey` module, `tools/journeys`, `temper/docs/design/client/journeys/`) are shared with whoever owns the web client: change only what your spec names there, additions only, and never touch the browser's recordings or prints. `ui-stop-coding-row` edits `temper/tests/one-process` and jig's routing; `ui-live-cheap-2` edits `temper/crates/temper/tests/support/forge_land.rs` and `tests/suite/forge_land.rs`: none is yours. Keep your hunks to what your spec names; never reformat or move what you don't change.
