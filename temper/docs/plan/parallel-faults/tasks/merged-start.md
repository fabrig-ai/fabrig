# A merged start checks out each merge it commits

## Goal

A task with `after` starts from `Start::Merged`. The worker merges each head with `git merge --no-commit` and records it with `commit-tree`, which by `git.md` 4.7 moves neither HEAD nor the merge's state, and nothing checks the commit out. So the agent is handed HEAD at the base's tip, `MERGE_HEAD` present, `git status` saying "All conflicts fixed but you are still merging": the request's item 6, "half-merged". With two heads the second `git merge` is refused, "You have not concluded your merge", exit 128 (run by hand with git 2.47 on 2026-11-06), which by `hold.rs`'s `Merge` arm ends the preparation `Failure::Transient`, so a multi-head early start may never prepare at all. The tests are green because the worlds' fakes clear the merge on commit, which real git doesn't.

Acceptance:

- After each `CommitHead`'s `Committed`, the worker checks that commit out, `clean: true`, before the next head or `Ready`.
- `temper-fake-git` refuses a merge while one is in progress, as git does, so the state test fails without the fix.
- A two-head merged start's op order, in `merged_heads_commit_each_merge_in_order`, checks out each commit, and on `temper-fake-git` that order's commands end with HEAD on the last commit and no `MERGE_HEAD`.
- Saves and delivery still commit on `tips.head`, and `merged_heads_commit_each_merge_in_order`'s last lines hold as they are (`Done::Unchanged`, `commit(12)` pushed).
- `Start::Merge`, a merge in progress handed to the agent on purpose (`worker.md`, section 5), is untouched.
