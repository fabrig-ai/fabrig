# ui-long-redirect: what every task holds to

- **Focused and fuzzy alone.** Never `tools/tiers/run`, a `<tier>-<tree>` profile,
  `scripts/browser.sh`, a walk, a render check or a throwaway driver. A story in a slow
  tier is written and compiled (`--no-run`), not run: say so in the report.
- **Tests stay cheap.** A new case of one behaviour is a row of the existing table test
  the spec names, beside its siblings' fixture; a new test is only one the spec
  sketches. No test reaches a real host.
- **The failing rows first.** Write the spec's rows, run them on your branch's base, see
  each fail for the rule's reason, then build. The report quotes the failure seen.
- **A new test must bite** (the implementer's text): break the rule once by hand, see
  the row fail, restore.
- **No live code.** The person's own callback URL held a live code: never ask for it,
  search for it or reproduce it. Every code, state, client id and cookie in a test is
  synthetic, built from the generators in `contracts.md`, section 5.
- **The shapes are `temper/docs/plan/ui-long-redirect/notes/contracts.md`'s.** A name,
  field, signature, constant, value or page text it gives is spelled as it gives it. One
  it doesn't give is yours, inside your files.
- **skein names no application.** No skein file names temper, jig or smith: the
  listener's page names the application its owner gives (`contracts.md`, section 3).
- **A branch stays in its tree, but for what the spec lists.** A skein task's edits in
  jig and smith are the lines its spec's `Owns and may change` names, each only what the
  skein change forces there (a field's value, a call's argument, a match's arm, the
  accessor named); anything more is a `Question:`.
- **`docs/design/` stays closed** but for the status bullet a spec says to delete, as a
  stated departure from the implementer's text: the design is written, and its status
  must say what is built when the branch lands.
- **No stored format, wire or refusal vocabulary changes.** The client wire, the store's
  records and `Refusal`/`Unusable` stay as they are; a change that would touch one is a
  `Question:` first.
- **Generated files your change makes stale are yours,** regenerated by their own tool,
  never by hand, and named in the report with what moved.
- **Before calling a failure "outside the change",** run it once on the pristine base.
  If the base passes and your branch fails, it's yours.
