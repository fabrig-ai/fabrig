# survey-answer: what every task holds to

- **Focused and fuzzy alone.** Never `tools/tiers/run`, a `<tier>-<tree>` profile,
  `scripts/browser.sh`, a walk, a render check or a throwaway driver. No task here adds a
  slow-tier story.
- **Tests stay cheap.** A new case of one behaviour is a row of the existing table test
  the spec names; the one new story is the one `answer-room` sketches, in the agent's
  process world on skein's simulated kernel, below the real loop. No test reaches a real
  host or provider.
- **The failing test first.** Write the spec's rows, run them, see them fail for the
  rule's reason, then build. The report quotes the failure seen.
- **A new test must bite** (the implementer's text): break the rule once by hand, see the
  row fail, restore.
- **The words and the rule are `temper/docs/plan/survey-answer/notes/contracts.md`'s,**
  spelled as it gives them. A name it doesn't give is yours, inside your files.
- **No stored format or protocol changes.** A sub-agent's answer is text inside a tool
  result: its words and its length change, no record, schema, vocabulary or wire does.
  A change that would touch `smith-transcript`, `smith-channel`, `smith-events`' records,
  a schema file or a recorded fixture under `smith/benchmarks/tests/recorded/` is a
  `Question:` first.
- **Trees.** Both tasks are smith's. smith names neither jig nor temper. A jig or temper
  test your change makes red is a reader to report, never a file to edit, unless the spec
  lists it.
- **Step code** (`smith/AGENTS.md`): production domains (`smith-domain-run`,
  `smith-domain`) use no own-enum `if let` or `let else`, tuple scrutinees, closures,
  `loop` or `while`; no indexing, no unchecked arithmetic, no `as`, no `unwrap`.
- **Generated files your change makes stale are yours,** regenerated by their own tool,
  never by hand, and named in the report with what moved.
- **A measured memory ceiling** a world's fixed scenario now passes because of your
  change moves by hand, as `smith/docs/design/protocol/limits.md`, section 5 has it: to
  the new peak with the headroom the ceiling's own comment gives. The report names it
  with both figures and the limit that moved it. A CPU budget or a timeout never moves.
- **`docs/design/` stays closed** but for the status lines a spec says to delete, as a
  stated departure from the implementer's text: the design is written, and its status
  must say what is built when the branch lands. Delete only your own lines; the other
  task deletes its own beside them.
- **Before calling a failure "outside the change",** run it once on the pristine base.
  If the base passes and your branch fails, it's yours.
