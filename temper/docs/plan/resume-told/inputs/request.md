# resume-told: a producer resuming after an answer knows what it's looking at, and keeps its work

From temper/qa's parallel replay of a real plan on a real deployment, 2026-11-06, at `5d0044254f`: 8 producers at once, a goal ended by itself. Its evidence is outside this repository, so the words here are what you have. Causes are from reading a run and the design, not reproduced: reproduce each first in the lowest tier, and say if one's wrong.

**What happened.** A producer parks on a question while other tasks land in its goal branch. On its answer, the next run starts with a merge of the goal tip in progress (`temper/crates/temper-engine-domain-forge/src/items.rs`, `merge_landing`; `temper/docs/design/domain/worker.md`, section 5, **A merge in progress**), which is by design. Nothing tells the run. It finds `MERGE_HEAD` and 46 to 53 staged files of other tasks in its checkout, and it reads them as contamination.

- **Two tasks, 4 of their 8 runs, and 3 foremen** went on this. One run: "Stopped, touching nothing: `git rev-parse -q --verify MERGE_HEAD` now prints … status instead shows ~46 unrelated staged skein civil/env/codec edits and none of my docs/test followup. This is an active merge, contrary to the prerequisite. Please isolate/stabilize my tree and recover my followup". Another: "Were these intentionally overlaid inputs for this activation? … B restore isolation before I continue."
- **The answers it got were guesses, and one was harmful.** A foreman, seeing the same files, told a run to do "the cleanup yourself: don't deliver those edits", which removes the merge's content. The goal's tick said "the design doesn't promise that uncommitted edits survive a resume", and sent a run to `git fsck`. Only later did one answer "Your tree is not contaminated, so leave the merge in place", having worked it out from `temper help change`'s one sentence, "Answered producers retain delivered work and merge the moved goal tip."

**What's wanted, ranked. Drop from the bottom if this grows past three or four tasks, and say what you dropped:**

1. **A resumed run is told, in what it reads, before it looks.** Which commit is its head, that the staged files are the goal tip's merge (its `MERGE_HEAD`), that it leaves them alone and carries on, and that its push commits the lot as the merge. Say what the conflict case adds. Or, if it's simpler and can't be misread, a clean merge is committed before the run starts, so that it sees a clean tree with its own work and one new commit, and `temper/docs/design/protocol/git.md`, 4.6 and `worker.md`, section 5 move: decide which, say why, and take the one with less to go wrong. `landing-fixes/resume-merge` is on this code and asks no merge when the branch already holds the tip: **this plan stands on it.**

2. **Does a parked run's work survive? Prove it.** `worker.md`, section 5, **Saved work**, says a run resuming from saved work starts where the last one stopped, but a run reported its uncommitted edits gone, and its edits weren't in `git status`. They may simply be in its head now. Failing first, in the lowest tier that holds a real checkout: a producer with committed and uncommitted edits parks on a question; the goal branch moves; on the answer its next run has every edit, and delivering lands them. If they can be lost, fix that. If they can't, say so plainly in what the run reads, and in item 3.

3. **Whoever answers it knows too.** `temper/docs/help/change.md` says what a resumed producer's checkout holds, enough that a foreman and a goal's agent answer rightly from it, within the page's bound. The coding charter (`temper/crates/temper-service/src/stock/coding.txt`) gets only what the run can't be told at its resume. A stock charter's words are forge's here. The foreman's are too.
