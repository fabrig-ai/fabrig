## Goal

No page claims empty until its read has answered. Home said "No chats yet." and "Nothing needs you. Work carries on…" while Behind, with T1 live. While a read hasn't answered, on first load or after the link comes back, a page keeps what it last knew, and with nothing known it draws the section's title with no line under it.

Two causes, both read from the code and not yet run:

- **The views ask only whether a list is empty.** A watch backing off its opening is Behind with no `latest` (`jig-client-domain/src/watches.rs`), so Home's `needs` and `chats` find nothing and say so. That fits the walk's Behind with T1 live, but nobody has reproduced the walk itself, and the ruling holds whatever provoked it.
- **The domain treats a lost read as an answer.** `Chats::told` sets `page = None` and `page_delivered = true` on any closed read, including `ReadNone::Unreachable`, which jig gives a read whose connection went. `Goals` drops its page the same way, and `HasGoals` forgets it had ended goals. `Inbox::delivered` turns true when a section's read was refused, so its empty cards count as known. `delivered` also turns false during each refresh, which blanks Needs you and Home's headline.

Acceptance:

- The tests of Steps, 5, pass, and each is seen red without its rule.
- Behind with an unanswered read draws no empty claim on Home, Chats, Needs you, the terminal's Inbox or Goals.
- An answered empty read still says it on each.
- A lost read drops nothing that was known.
- The **Not yet** entry of Steps, 6, is gone.

## Steps

1. **`Inbox`** (`temper-client-domain/src/pages/inbox.rs`):

   ```rust
   impl Inbox {
       /// Whether this section's read has answered with its value since the page opened
       /// (temper/docs/design/client/README.md, 3.5).
       #[must_use]
       pub const fn answered(&self, group: InboxReadGroup) -> bool;
       /// The needs' read has answered and every card read it sent has: what the cards say
       /// stands, through each later refresh, until the next answer changes it.
       #[must_use]
       pub const fn known(&self) -> bool;
   }
   ```

   - A section is answered where `apply` finds its `arrived` page. With no filter, both are answered where `refresh` finds a `Delivery::Inbox`.
   - `known` latches in `told`, the first time the needs are answered and `delivered(source)` holds.
   - An `Inbox` lives as long as its page, so neither is ever reset.

2. **`Chats` and `Goals`:**

   ```rust
   impl Chats {
       /// The live watch has delivered and the closed read has answered with its value, for this query.
       #[must_use]
       pub fn known(&self, client: &Client) -> bool;
       /// The notes read has answered with its value, for the Drafts filter.
       #[must_use]
       pub const fn documents_known(&self) -> bool;
   }
   impl Goals {
       #[must_use]
       pub fn known(&self, client: &Client) -> bool;
   }
   ```

   - `Chats::told`: a closed read without a value keeps `self.page`, and sets `page_delivered` as it does today. A private `page_answered` is set only on a value and cleared where `configure` clears `page`.
   - `documents_known`: set where `notes_told` takes a value, cleared in `open_documents` and `close_documents`.
   - `Goals::told`: a read without a value keeps `self.page` and leaves `self.count` alone: adding the kept rows again would double them when `first` is false. It still clears `reading_page`. Its `page_answered` is cleared where `configure` clears `page`.
   - `HasGoals::told`: a read without a value keeps `self.ended`, so a lost read can't turn Home from its goals section to its chats section.
   - `known` is `page_answered` and the live watch's `live(client)` being `Some`.
